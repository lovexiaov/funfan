# FunFan · UI/UX 复审（2026-11-01）

> 复审范围：`FunFan/Theme.swift`、`Views/`（Popover / 设置 / 曲线 / 规则 / 组件 / 焦点环）、`App/AppDelegate.swift` 的窗口与浮层装配。
> 复审方法：源码逐处核对 + **真机渲染色板取样**（离屏渲染 2x，逐像素取色后按 WCAG 2.1 相对亮度公式实测对比度）+ 实机截图对照。
> 结论先行：**要求 2（配色清晰、层级分明、对比度、语义一致）在深色模式下基本成立，在浅色模式下系统性失效；要求 1（明暗自动切换 + 手动覆盖 + 切换时机）只完成了「跟随系统」这一条，且是以「界面自动变浅、强调色不变」的坏方式完成的。**

---

## 0. 一个必须先说的前置问题：浅色模式从来没被看过

`FunFan/DevTools/RenderCheck.swift:126`：

```swift
let base = AnyView(content.environment(\.colorScheme, .dark))
```

设计走查工具把 `colorScheme` **写死成 dark**。项目里所有 `--render` 截图（含 `docs/ui-prototype/*-actual.png`）都是深色，浅色模式零证据。

而产品侧其实**没有任何外观开关**（全仓 `preferredColorScheme` / `NSAppearance` / `appearance` 命中 0 处，`SettingsStore` 无外观键），也就是说：系统一旦是浅色，用户看到的就是一个从未被设计过、也从未被看过的界面。

本次复审临时给走查工具加了 `--scheme light` 才拍出真实浅色画面（证据见 `docs/ui-prototype/popover-light-review.png`、`settings-light-review.png`），**结论很直接：当前浅色模式不可交付**。补丁见 §5.6，建议第一步就合进去，否则后面的修复无法验收。

## 1. 两条要求的落地判定

| 要求 | 判定 | 依据 |
|---|---|---|
| 1a 明暗随系统自动切换 | ⚠️ 形式上生效，效果不可用 | 未硬编码外观，窗口底色 / 卡片底 / 文字走系统动态色，会跟着系统变；但**四个语义色是静态 RGB，不跟着变** → 浅色下全部失效（§2 P0-1） |
| 1b 手动覆盖（跟随 / 浅 / 深） | ❌ 未实现 | 无设置项、无持久化键、无应用逻辑 |
| 1c 切换时机与表现 | ❌ 未定义 | 系统切换时 SwiftUI 会即时重绘，但此刻界面处于「底色浅了、强调色还亮着」的半新半旧态；无过渡、无走查手段验证 |
| 2a 主次层级分明 | ⚠️ 部分成立 | 深色下数据层级清楚；但字号散了 13 档、分组标题是全页最淡的文字、警告文案比正文更小（§2 P1-2/P1-3） |
| 2b 对比度满足可读性 | ❌ 深色勉强过、浅色全线崩 | 中性色 `.tertiary` 浅 1.82:1 / 深 2.29:1；语义色浅色 1.28–2.52:1（实测表见 §4） |
| 2c 语义色使用一致 | ❌ 一色多义 | accent 同时是「可点击」「品牌」「自动接管中」「数据曲线」；warm 同时是「温度偏高」和「界面注意事项」；hot 同时是「过热」「报错」「禁区」（§2 P0-2） |

注：`docs/ui-design-handoff.md` 的 H4 已确认「v1 即支持双主题（令牌已预留）」，`§7 验收清单` 也写了「对比度 ≥ WCAG AA (4.5:1)」。这两条目前**均为未达成**，属于文档与实现脱节，需要在 SPEC/附录 C 里纠正，不能继续挂在「已实现」下。

## 2. 现有设计的优点（先肯定，这些不要改坏）

1. **令牌收口做对了**：`Theme.swift` 是唯一色彩入口，视图里没有裸色值（全仓 grep `Color(red:` 只在 Theme 出现）。这一点决定了后面的明暗改造是「改一个文件 + 加一层解析」，而不是满仓搜色值。
2. **温度三态有明确阈值常量**（`Theme.swift:17-18`，60/75℃）且**集成为一个函数** `color(forCelsius:)`，阈值调整只有一个落点。
3. **卡片 / 轨道 / 描边全部用 `Color.primary.opacity(...)` 派生**，而不是写死深灰。这是深色下层次成立的根本原因，也是浅色改造只需重定几个 alpha 就能救回来的一半工作量。
4. **语义化状态文案优于纯色**：冲突提示（`MenuBarView.swift:93-125`）把「谁在控制」和「我们做了什么」拆成两句，曲线窗口把「曲线给的」与「实际下发的」并列（`CurveEditorView.swift:76-88`）——这些是真正的信息设计，不是装饰。
5. **安全不变量做成了不可关闭的只读行**（`SettingsView.swift:89-96`），而不是给用户一个能把自己风扇锁死在手动的开关。正确的克制。
6. **焦点环按控件形状自绘**（`FocusRing.swift`），并为对比度/形状退化留了 macOS 13 分支。可访问性意识在线。

## 3. 问题清单（按严重度）

### P0-1 · 四个语义色在浅色模式全部低于可读下限

**位置**：`FunFan/Theme.swift:10,13-15`（定义处）；消费点遍布 `Views/`（`MenuBarView.swift:225,237,245,551,584`、`SettingsView.swift:76,155,227,256`、`RulesView.swift:73,155`、`CurveEditorView.swift:85,190,193,252`）。

**现象**：浅色下主色文字（「展开各核心温度」「编辑曲线…」）像水印；温度数字（45°/37°/35°）像禁用态；设置页那条黄字警告基本读不出来；风扇环弧线在白底上几乎看不见。

**实测**（WCAG 2.1，含透明度按实际合成后取值）：

| 令牌 | 值 | 深色底 #1C1C1E | 深色卡片 #2A2A2E | **浅色底 #ECECEC** | **浅色卡片 #E2E2E2** |
|---|---|---|---|---|---|
| accent | `#46C8FF` | 8.89 ✅ | 7.48 ✅ | **1.62 ❌** | **1.48 ❌** |
| cool | `#4CD988` | 9.39 ✅ | 7.90 ✅ | **1.53 ❌** | **1.40 ❌** |
| warm | `#FFBD4B` | 10.24 ✅ | 8.62 ✅ | **1.41 ❌** | **1.28 ❌** |
| hot | `#FF5F5F` | 5.72 ✅ | 4.81 ✅ | **2.52 ❌** | **2.30 ❌** |

**原因**：这四色是按 `#1C1C1E` 深底调的「高亮度低饱和」色。亮度一旦接近白底，对比度必然塌到 1.3–2.5。这不是「差点火候」，是**方向错**：同一个色值不可能同时服务浅底和深底。

**改法**：令牌按外观分叉（§5.1），浅色用深一档的同色相，并区分「文字用」与「图形用」两个强度（图形 ≥3:1 即可，文字要 ≥4.5:1）。已实测合格的候选见 §4.2。

### P0-2 · 一色多义：同一个色承担 3 种互不相干的含义

**accent（`#46C8FF`）同时是**：
- 可点击（`MenuBarView.swift:225` 展开核心、`567`/`597` 编辑规则/曲线、`FocusRing.swift:45` 焦点环、`Components.swift:31,35` 选中态）
- 品牌（`MenuBarView.swift:65` 头部风扇图标）
- **自动化正在接管**（`MenuBarView.swift:551`「规则接管中 · N RPM」、`584`「曲线接管中」、`RulesView.swift:155`「触发中」胶囊、`CurveEditorView.swift:85` 下发 RPM）
- 数据图形（`CurveEditorView.swift:229,239` 曲线本体、`MenuBarView.swift:653` 风扇环弧）

后果：把状态文字刷成链接色，用户会去点「规则接管中」；反过来「编辑曲线…」和状态文字同色同字号，可点与不可点失去区分。

**warm（`#FFBD4B`）同时是**：温度偏高（60–75℃，`Theme.color(forCelsius:)`）＋ 界面需要注意（`MenuBarView.swift:98,505` 未装 helper、`123` 冲突条底色、`SettingsView.swift:256,277` 免责声明、`155` 待批准）。这两套「标尺」混在一个色相里，会导致：免责声明（一个永久性的法律说明）看起来和「CPU 62℃」是同一级别的告警。

**hot（`#FF5F5F`）同时是**：过热（≥75℃）＋ 报错（`SettingsView.swift:76,161`、`MenuBarView.swift:533`）＋ 禁区（`CurveEditorView.swift:190,193` 安全下限红带）。曲线窗口里红带其实是「安全兜底区」，语义上是**保护**而非**危险**，但和「过热红」共用一色，容易被读成「这一大片是过热区」。

**cool（`#4CD988`）同时是**：温度正常（默认态）＋ 充电中（`MenuBarView.swift:412`）。

**改法**：拆成两套语义轴，不共用色值（§5.3）：
- **温度轴**（数据语义，只用于指标本身）：cool / warm / hot，只出现在小圆点、进度条、图表描边上；
- **界面轴**（动作语义）：info=accent（只给可点击与品牌）、attention=amber、error=red。

### P0-3 · 「默认一切正常」被画成了绿色：颜色没带信息，还压了数值层级

**位置**：`MenuBarView.swift:237,245`（`tempChip` 的圆点与数字都取状态色）、`320-333`（`coreTile`）、`345`、`376`。

**现象**：深色截图上四个温度全是绿点绿字。绿 = 「<60℃」= 绝大多数时候的默认状态，于是**最常出现的画面里，颜色传递的信息量是 0**；同时四个本应是「主数据」的数字被降级成彩色文本，与旁边真正的次要信息（`区间`、`传感器数`）抢注意力。到了 75℃ 才变红这件事，用户第一次是看不出来的——因为他没见过别的样子。

**补充**：颜色是唯一编码（点 + 文字双重着色），色觉障碍用户完全拿不到状态。

**改法**：数值保持 `primary`，状态用**一个小色标 + 形态差异**表达（正常=实心细点；偏高=实心点+数字加粗；过热=点+三角图标+文字 weight/size 提升）。这样「没有颜色」反而是正常的、安静的，异常才跳出来。

### P0-4 · 中性文字层级本身就不够：`.tertiary` 在两种外观下都阅读失败

**位置**：`Theme.swift` 无三级文字令牌，视图直接调系统 `.secondary`（34 处）/`.tertiary`（22 处）。典型：`MenuBarView.swift:72`（相对时间）、`72/179`（传感器数）、`277/291`（核心布局注释）、`609`（采样耗时）、`RulesView.swift:168`（迟滞）、`CurveEditorView.swift:285,293`（坐标轴 8pt）、`SettingsView.swift:291`（分组标题）。

**实测**：

| 层级 | 浅色底 | 深色底 |
|---|---|---|
| primary | 17.78 ✅ | 15.63 ✅ |
| secondary | **3.84 ❌**（需 4.5） | 5.76 ✅ |
| tertiary | **1.82 ❌** | **2.29 ❌** |

**原因**：`.tertiary` 是系统给的「说明性文字」色，设计意图就是「弱化到快看不见」。但本项目 22 处 `.tertiary` 里有相当一部分承载**必要信息**（坐标轴刻度、迟滞值、传感器数、分组结构），并且字号压在 8–10pt。弱色 + 小字 = 双杀。

**改法**：定义 `textPrimary / textSecondary / textTertiary` 三档并**实测达标**（浅色 secondary 提到 `#5A5A5A`≈5.9:1、tertiary 提到 `#6E6E73`≈5.0:1）；`.tertiary` 只留给真正的装饰性文字（例如曲线图的网格标签），且不小于 10pt。

### P1-1 · 无外观设置：没有手动覆盖，也没有「跟随系统」的显式表达

**位置**：`SettingsView.swift`（通用分组只有两项）、`SettingsStore.swift`（无外观键）。

**影响**：三类用户都受影响：① 系统浅色用户没法切深色避开 P0-1；② 系统深色用户想固定深色（菜单栏工具常驻，很多人不希望跟着变）；③ 截图/录屏时无法固定外观。

**改法**：见 §5.2（三态 + 持久化 + 即时生效 + 不污染菜单栏）。

---

### P1-2 · 字号散了 13 档，且「越重要越小」

**位置**：全 Views 统计——8pt×5、9pt×19、10pt×37、11pt×31、12pt×4、13pt×2、14×1、15×3、19/20/22/24/26 各若干。100 余处字号声明里 **92 处 ≤ 11pt，24 处 ≤ 9pt**。

**具体错位**：
- 设置页最关键的那句阻断说明「当前未连接特权后台组件，只能监控、无法控制风扇」是 **10pt**（`SettingsView.swift:226-227`），比正文 12pt 更小；
- Popover 里「只能监控，还不能控制风扇」是 11pt semibold（`MenuBarView.swift:506`），而普通数据行也是 11pt/13pt（`detailRow`、`tempChip`）；
- 曲线坐标轴 **8pt**（`CurveEditorView.swift:285,293`）。

结果：层级靠「字号微差」传达（10 vs 11 vs 12），人眼分不出来；真正的优先级（阻断 > 错误 > 数据 > 元信息）与字号顺序**不一致**。

**改法**：收敛到 4 档 + 1 个数值档（§5.4），并把「阻断/错误」提到 12pt 起、走卡片容器。

### P1-3 · 分组标题是全页最淡的文字

**位置**：`SettingsView.swift:289-292`：

```swift
Text(title)
    .font(.system(size: 10, weight: .medium))
    .foregroundStyle(.tertiary)
    .textCase(.uppercase)
```

**问题**：结构信息（通用 / 风扇控制组件 / 诊断 / 关于）用全页最淡的色 + 最小字号 + 一个对中文**完全无效**的 `.uppercase`。截图里这四个标题读起来像禁用标签，用户扫不到分区。同源问题：`RulesView` 的「规则接管风扇」和头部信息挤在一行，没有分区感。

**改法**：11pt semibold + `textSecondary`（≥4.5:1）；中文去掉 `textCase`，改用「左侧 2pt accent 竖条 + 字重」建立分区；或直接改用 `Form`/`Section` 语义（但注意 §附录 C 里自绘控件的离屏渲染约束）。

### P1-4 · 卡片与页面底只差 5% alpha，浅色下层次消失

**位置**：`MenuBarView.swift:628-631`（`cardBackground` = `primary.opacity(0.05)`）、`SettingsView.swift:298-299`（`primary.opacity(0.04)`）、`RulesView.swift:197`、`CurveEditorView.swift:101,112`。

**实测**：浅色 卡片 `#E2E2E2` vs 底 `#ECECEC` = **1.10:1**；深色 = 1.19:1。深色还能靠「亮的东西浮起」读出来，浅色下 10/255 的差几乎不可见——截图里温度宫格、设置卡片边界都在飘。

**改法**：浅色改「白卡 + 6% 黑描边（或极轻投影）」，深色保留现有 derive 方式但把描边补上（`primary.opacity(0.06)` 0.5pt），让**描边**而不是**填充差**承担边界。

### P1-5 · 首屏出现裸命令行

**位置**：`MenuBarView.swift:483-487` 展示 `control.message`，未装 helper 时该文案是 `控制功能需要安装特权 helper: sudo bash scripts/install-helper.sh`。

**问题**：同一屏在 `helperPrompt`（`:500-540`）里已经给了「一键启用」按钮和更完整的人话解释，于是同一件事出现了两种表述，其中一种是让普通用户去开终端。深色截图里这行黄字就在策略分段控件正下方。

**改法**：`control.message` 里不要出现 shell 命令（命令只留在 `installer.note` / 诊断报告）；未就绪时抑制这条 message，只留卡片。

### P2-1 · 每张卡片的最后一行都多一条分割线

**位置**：`SettingsView.swift:333` —— `SettingRow` 无条件追加 `Divider()`。三个分组卡片底部各挂一条悬空短线（截图可见）。改成「行前分隔 + 首行不画」或在 `section` 里判定 `isLast`。

### P2-2 · 原生控件与自绘控件混用，同一窗口两套视觉语言

**位置**：自绘：`Components.swift` 的 `StrategySegmented` / `FunFanToggle` / `FunFanButton`。原生：`RulesView.swift:55-62`（`添加规则`，`.controlSize(.small)`）、`:123`（`恢复示例规则`）、`:176-190`（`slider.horizontal.3` / `trash` 两个 `.borderless` 图标按钮）、`RulesView.swift:299,332`（`TextField(.roundedBorder)`）、`:308,347,373`（`Picker` / `Stepper`）。

**问题**：圆角（6 vs 系统）、字重、悬停态、焦点态、甚至色温都不一致；规则窗口右上角那个原生按钮的蓝色明显偏冷、和 `Theme.accent` 不是同一个蓝。更实际的风险：`.borderless` 图标按钮**没有焦点环**（`funfanFocusRing` 没套），全键盘用户 Tab 到删除键时看不到焦点。

**改法**：规则窗口的表单类控件可以用原生（TextField/Picker/Stepper 自绘成本高），但**动作按钮统一回 `FunFanButton`**，并给编辑/删除图标补焦点环与 accessibleLabel。若决定接受原生，则应在附录 C 明确记录「哪些位置刻意保留原生」，避免下次复审重复提问。

---

### P2-3 · 焦点环是 accent，浅色下 1.6:1

`FocusRing.swift:45` 用 `Theme.accent` 画 2pt 环。WCAG 2.4.11/1.4.11 要求焦点指示 ≥3:1。深色 8.89 ✅，浅色 1.62 ❌。随 §5.1 的浅色 accent（图形档 `#0B84B8` ≈3.56:1）一并解决。

---

### P2-4 · 曲线窗口的红色带语义容易被反读

`CurveEditorView.swift:186-197`：红带 = 「你画不到的地方（安全下限以下）」，同一窗口的红也用于「过热」语义。而红带面积很大（截图右半屏），第一眼像「过热区/危险区」。文字说明（`:67`）压制不住。

**改法**：禁区改用「斜纹/中性灰 + 边界虚线」，或在带内加 9pt 文案「安全下限」。红色只留给「≥75℃」。

---

### P2-5 · 开发者遥测常驻在用户界面

`MenuBarView.swift:606-612`：「采样 21 ms」+ 诊断信息摘要，9pt tertiary，永远显示。这是给排障用的，不该占用首屏底栏的固定位置（应只在 `--log` / 设置页诊断区出现，或超过阈值才出现）。

### 4.1 现状

见 §3 P0-1、P0-4 两张表（取值来自 2x 渲染逐像素采样，非估算）。

### 4.2 浅色模式候选色（已实测，可作为落码值）

| 令牌 | 深色（保留现状） | 浅色·文字档（≥4.5:1） | 浅色·图形档（≥3:1） |
|---|---|---|---|
| accent | `#46C8FF` | `#0A5F80`（底 6.00 / 卡片 5.47） | `#0B84B8`（底 3.55） |
| cool | `#4CD988` | `#136B37`（5.58 / 5.09） | `#1F8A4C`（底 3.70） |
| warm | `#FFBD4B` | `#7A4A00`（6.33 / 5.77） | `#B26A00`（底 3.59） |
| hot | `#FF5F5F` | `#B3261E`（5.53 / 5.05） | `#E5483F`（底 3.33） |

## 5. 可落地的改法

### 5.1 令牌层：从「静态常量」改成「由环境解析的双套调色板」

不改调用点写法（保持 `Theme.accent` 的可读性），只把取色改成走环境：

```swift
// Theme.swift（示意；色值用现有 Color(red:green:blue:) 写法即可，无需引入十六进制扩展）
struct Palette {
    let accentText, accentFill: Color   // 拆「可点文字」与「图形填充」
    let cool, warm, hot: Color          // 温度轴（只用于指标）
    let attention, error: Color         // 界面轴（只用于提示）
    let cardFill, cardStroke: Color

    static let dark  = Palette(accentText: Color(red: 0.275, green: 0.784, blue: 1.000), /* … 现有值 */)
    static let light = Palette(accentText: Color(red: 0.039, green: 0.373, blue: 0.502), /* … §4.2 */)
}

extension EnvironmentValues {
    var palette: Palette { get set }   // 默认 .dark，由根视图按 colorScheme 注入
}
```

根视图统一注入：`.environment(\.palette, colorScheme == .dark ? .dark : .light)`。

**为什么不直接上 `Assets.xcassets` 的 Color Set / `NSColor` 动态色**：那两条路都靠 AppKit 的 `NSAppearance.current` 解析，而 `ImageRenderer` 离屏渲染不保证设置它——也就是说改造完你会**再次失去浅色走查能力**，回到 §0 的盲区。环境驱动是唯一能同时满足「跟随系统 / 可覆盖 / 可离屏走查」的方案。

### 5.2 外观设置：三态 + 即时生效 + 不碰菜单栏

```swift
enum AppearancePreference: String, CaseIterable { case system, light, dark
    var colorScheme: ColorScheme? { switch self { case .system: nil; case .light: .light; case .dark: .dark } }
}
```

- `SettingsStore` 加 `@Published var appearance`，写 `UserDefaults`（键 `FunFan.appearance`，默认 `.system`）；
- 四个根视图（Popover / 设置 / 曲线 / 规则）都 `.preferredColorScheme(settings.appearance.colorScheme)`；
- **`SettingsStore` 必须以 `@ObservedObject` 传进每个根视图**（现在 `CurveEditorView`、`RulesView` 根本没拿到 settings）。否则「已开着的窗口」不会跟着设置变，只有重开才生效——这就是「切换时机」最容易踩的坑：用户改了设置，看到的却是旧外观。

**不要用 `NSApp.appearance` 做全局覆盖**：菜单栏图标与标题由系统按菜单栏实际外观绘制，全局反转会造成「浅色菜单栏配深色文字」这类不可读组合（此项需真机复验，但风险明确，没有理由用全局方案）。

**切换时机的行为定义**（写进 SPEC）：
1. 系统切换 → `colorScheme` 环境值变化 → SwiftUI 即时重绘，无需任何通知代码；
2. 手动切换 → 立刻对**所有已打开窗口**生效，不重开；
3. Popover 开着时切换，不得闪烁或丢高度（`preferredContentSize` 联动在 `AppDelegate.swift:270-277`，改色不触发尺寸变化，风险低，但要验一次）。

### 5.3 语义色分工（写进 SPEC，作为后续新代码的约束）

| 轴 | 令牌 | 允许出现在 | 禁止出现在 |
|---|---|---|---|
| 温度 | cool / warm / hot | 圆点、条、图表描边、拓扑方块 | 数值文本、按钮、提示条 |
| 界面 | accentText | **可点击**文案、链接式动作 | 状态描述、数据 |
| 界面 | accentFill | 选中底、曲线、环弧、焦点环、品牌图标 | — |
| 界面 | attention | 阻断/待办提示条（图标 + 容器） | 温度、法律说明 |
| 界面 | error | 失败原因、不可恢复错误 | 温度、禁区 |

同时立两条硬规则：
- **数值永远用 `textPrimary`**，颜色只加在指示物上（解决 P0-3）；
- **状态不能只靠颜色**：过热必须同时有图标或字重变化（色觉障碍）。

### 5.4 字号刻度：13 档 → 4 档 + 1 个数值档

| 用途 | 字号 | 备注 |
|---|---|---|
| 窗口标题 | 15 semibold | 现状保留 |
| 分组标题 | 11 semibold | 不再用 tertiary |
| 正文 / 行标题 | 12 | 设置行、规则名 |
| 元信息 | 11 (≥4.5:1) | 替换掉 9/10pt 的说明文字 |
| 数值 | 19–20 medium monospaced | 现 `valueFont` |

硬下限：**正文与元信息不小于 11pt**；坐标轴等纯图形标注可到 10pt，但必须用 `textSecondary`（≥4.5）。当前 24 处 ≤9pt 全部要落到这条线以上。

### 5.5 卡片层次

浅色：卡片 `#FFFFFF` + `strokeBorder(black.opacity(0.06))` + `shadow(black.opacity(0.04), radius: 1, y: 0.5)`；深色：保留 `primary.opacity(0.05)` 但补 `primary.opacity(0.06)` 0.5pt 描边。边界由描边承担，不再依赖 5% 填充差。

### 5.6 走查工具补 `--scheme`（3 行，建议第一个合）

```swift
let scheme: ColorScheme = CommandLine.arguments.contains("--scheme")
    && CommandLine.arguments.last == "light" ? .light : .dark
let base = AnyView(content.environment(\.colorScheme, scheme))
```

用法：`./.build/debug/FunFan --render popover /tmp/popover-light.png --scheme light`。没有它，本次复审发现的浅色问题在修复后依然无法验证。
